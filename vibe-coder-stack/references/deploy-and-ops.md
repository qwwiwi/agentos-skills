# Деплой, проверки, секреты, серверы

Всё ниже проверено на наших проектах. Источник каждого правила – в [owner-corrections.md](owner-corrections.md).

## 1. Деплой только из git

На сервер попадает только то, что есть в коммите на `origin`. Никаких правок «прямо на сервере»,
никаких копий из рабочей папки.

Скрипт деплоя по шагам:

1. Отказ, если в рабочем дереве есть незакоммиченные изменения.
2. Отказ, если коммита `HEAD` нет ни в одной ветке `origin/*` (после `git fetch origin`).
3. Стадия собирается из коммита: `git archive HEAD <папка> | tar -x -C <stage>`, а не из рабочей папки.
4. Локальные проверки на стадии (битые ссылки, сборка).
5. Выкладка: `rsync -az --delete` в новую папку релиза.
6. Переключение симлинка `current` на новый релиз, рестарт процесса.
7. Проверка живого сайта в браузере.

```bash
#!/usr/bin/env bash
set -euo pipefail

echo "deploy: checking working tree"
if [[ -n "$(git status --porcelain)" ]]; then
  echo "deploy: working tree is dirty, commit first" >&2
  exit 1
fi

git fetch origin --quiet
if [[ -z "$(git branch -r --contains HEAD --list 'origin/*')" ]]; then
  echo "deploy: HEAD is not on any origin/* branch, push it first" >&2
  exit 1
fi

STAGE="$(mktemp -d)"
trap 'rm -rf "$STAGE"' EXIT
echo "deploy: building stage from $(git rev-parse --short HEAD)"
git archive HEAD site | tar -x -C "$STAGE"
# ... checks, rsync, symlink switch, restart
```

## 2. Релизы и проверка «что реально запущено»

- Выкладывай в `releases/<sha>-<время>/`, запускай из симлинка `current`. Откат – переключить симлинк обратно.
- Старые плоские папки рядом с `releases/` – мусор. `grep` по ним даёт ложный вывод «фикс не задеплоен».
- Проверять надо живой процесс, а не путь:

```bash
PID=$(systemctl show my-app -p MainPID --value)
readlink "/proc/$PID/cwd"     # the release directory the process actually runs from
```

- При разборе инцидента читай код задеплоенного релиза, а не свою локальную копию: локальная копия часто отстаёт от прода.

## 3. Staging → prod

- Сначала стенд (отдельный поддомен или зеркало), потом прод.
- Прод – отдельной командой и только после явного «да, на прод».
- После каждого выката на прод – Playwright по живому домену: телефон (390 px) и десктоп (1440 px), скриншоты, клик по изменённому сценарию. `curl` доказывает только, что файл доехал.
- Если у сайта есть зеркало, деплой идёт на оба адреса одной процедурой.

## 4. Проверки без CI: check.sh + pre-push

GitHub Actions не используем. Те же проверки идут локально и не дают запушить сломанное.

```bash
#!/usr/bin/env bash
# scripts/check.sh
set -euo pipefail
echo "check: typecheck"; npm run typecheck
echo "check: lint";      npm run lint
echo "check: tests";     npm test
echo "check: build";     npm run build
echo "check: ok"
```

```bash
#!/usr/bin/env bash
# .githooks/pre-push
set -euo pipefail
bash scripts/check.sh
```

```bash
git config core.hooksPath .githooks
chmod +x .githooks/pre-push scripts/check.sh
```

Вывод `check.sh` вставляй в описание PR – это и есть отчёт о проверке.

Тесты: приоритет – интеграционные на бэкенде (права, оплата, доступ). E2E – только для критичных
сценариев (оплата, вход). Тест, который чаще ломается сам, чем ловит баги, – удалить.

## 5. Секреты

- Токены, ключи, пароли – только в `.env` на сервере. В репозитории – `.env.example` без значений, `.env` в `.gitignore`.
- Не вставлять секреты в чат с агентом и не просить агента их вывести. Чат с агентом могут увидеть другие.
- Не печатать `.env` и переменные окружения целиком: только имена или отфильтрованный вывод.
- Логи бота содержат токен: HTTP-клиент пишет URL `api.telegram.org/bot<TOKEN>/...`. Хвост логов – только через фильтр:

```bash
journalctl -u my-bot -n 100 | sed -E 's#bot[0-9]+:[A-Za-z0-9_-]+#bot<REDACTED>#g'
```

- Тесты никогда не читают боевой `.env`: иначе тестовый прогон шлёт настоящие сообщения настоящим людям.
- В публичном репозитории – ни IP серверов, ни логинов, ни Telegram ID, ни почт.
- Токен утёк наружу (публичный репозиторий, канал, общий лог) – перевыпустить сразу.

## 6. Серверы и 152-ФЗ

Сначала вопрос «чьи это данные», потом выбор сервера.

| Ситуация | Где держать базу |
|---|---|
| Пользователи из РФ, собираешь имя, телефон, email | российский сервер: Timeweb Cloud, Yandex Cloud, VK Cloud, Selectel |
| Аудитория не из РФ | Hetzner, DigitalOcean – дешевле и удобнее |
| Смешанная | разделять: данные граждан РФ – на российском сервере, остальное – где удобно |

Плюс наше внутреннее правило: данные, выгруженные из Telegram (подписчики, переписки, аналитика каналов),
на российские серверы не выносим – они живут на зарубежном.

## 7. Ловушки хостинга и Cloudflare

- **Российские провайдеры режут соединения с Cloudflare после ~16 КБ** (с июня 2025). Сайт на российском сервере за прокси Cloudflare у части посетителей «висит»: мелкие файлы грузятся, крупные – нет. Решение – DNS-only (серая тучка), HTTPS выпускает сам веб-сервер (Caddy).
- **С российского сервера `api.telegram.org` часто недоступен.** Бота держи на зарубежном сервере; если API на российском, а бот – нет, связывай их очередью в базе.
- **Telegram не может скачать картинку по URL с российского хоста** (`sendPhoto` → 400 «failed to get HTTP URL content»). Проверка `curl` с твоей машины ничего не доказывает. Загрузи картинку боту один раз, сохрани `file_id` и шли по нему.
- **Западные узлы Cloudflare периодически не доходят до российского origin** (5–9% ошибок 520 и таймаутов у мониторинга). Это не твой код; российские посетители обычно ходят через другие узлы.
- **За Cloudflare IP клиента – из `CF-Connecting-IP`**, а не из `X-Forwarded-For`. Иначе лимит запросов «на IP» становится общим лимитом на узел Cloudflare и режет всех сразу.
- **Next.js и отсутствующая `NEXT_PUBLIC_*` переменная:** если переменной нет при сборке, сравнение не сворачивается в константу, и «мёртвая» ветка остаётся в бандле. Задай значение по умолчанию в `next.config.ts` (`env: { NEXT_PUBLIC_FLAG: process.env.NEXT_PUBLIC_FLAG ?? "false" }`).
- **Под `set -euo pipefail`** `grep -c` с нулём совпадений завершается кодом 1 и роняет скрипт. Если ноль – правильный ответ, пиши `grep -c … || true`.
- **Платежи – просто.** Таймеры, ретраи и состояние вокруг денег ломаются по-новому. Сначала ищи правило без состояния («кнопка оплаты есть, только если есть ссылка ровно под эту цену и срок»).
